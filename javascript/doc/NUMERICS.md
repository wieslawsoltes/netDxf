# Numerical compatibility

## Production and development references

The target is the pinned C# implementation's behavior, not whichever algorithm
is mathematically most accurate. Production `DotNetMath` uses the retained
`runtime/reference-math` backend. Its preferred source, generators and license
notices remain part of the package. `tools/HighPrecisionMath.mjs` is a separate,
development-only mathematical reference; it is not imported by the portable
entry or shipped as the production backend.

Source operation order, copies, signed zero, NaN behavior and software fused
multiply-add matter for binary64 comparison. Native host Math functions must not
replace the compatibility backend merely because they are faster or correctly
rounded on a sampled input. Exact gates do not admit rounding, tolerances,
expected-failure lists or input-specific expected-result tables.

GTE algorithms retain their original-path JavaScript mirrors, source/output
manifest and BSL-1.0 license. Generated-source equality is not independent
numerical qualification; eigen, root, interpolation and geometry results still
need the native comparisons defined by their corpora.

## Separate evidence categories

Production differential tests execute the actual pinned .NET methods and compare
full values/bits, including signed zero and the NaN distinctions required by the
corpus. Foundation, randomized geometry, primitive I/O and GTE stages are distinct
from direct transcendental comparisons. Agreement in one stage does not waive a
failure in another.

The independent mathematical audit compares HighPrecisionMath with an explicitly
installed MPFR library at two precisions. Its NaN-class comparison does not test
.NET's NaN payload/sign contract. Agreement after rounding is not a proof of
correct rounding for every binary64 input, and a successful development-reference
audit cannot override a production compatibility mismatch.

HTTP-origin and inline browser execution are separate requirements. They run the
native ESM implementation against digests derived from native results; expected
values must not be generated by the JavaScript implementation being checked.
Historical browser or numerical pass counts do not qualify current source.

## Reproduction

From `javascript/`, with the exact C# reference and toolchain selected:

```sh
export CONFIGURATION=Release # Repeat with Debug.
node tools/dotnet.mjs geometry
npm run verify:reference-math
npm run verify:exp-log
npm run verify:gte
npm run test:reference-math
npm run test:math
npm run test:geometry:exact
npm run test:gte
npm run test:math:independent
npm run benchmark:math
```

`MPFR_LIBRARY` selects the installed development library. The ctypes host ABI and
other platforms need their own qualification. Reports under ignored `artifacts/`
retain fingerprints, inputs, counterexamples, fatal/unavailable observations and
configuration. Source-guided tests and self-roundtrips are not native evidence.

Benchmarks distinguish host math, the production backend and the development
reference. Warmup, environment and workload are part of a result; descriptive
measurements do not establish speedups or release acceptance. Preserve correctness
and report the cost of exact arithmetic rather than changing expectations.
