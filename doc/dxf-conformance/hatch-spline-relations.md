# Stored HATCH spline relationships and weights

The typed HATCH reader previously accepted nonperiodic spline packets whose knot count, control count and degree disagreed, and accepted decreasing knot vectors. It then wrote those packets unchanged. A separate fidelity defect affected accepted optional weights: the reader stored group42 even when the rational flag73 was zero, but the writer omitted every such weight. An input weight2.5 therefore became the default1 after save and reload.

A before probe on the unchanged HATCH implementation reproduces all four cases in each of the six typed profiles and both input transports:36 malformed packets were accepted and reexported, and12 weight values were lost. Its successful mutation outputs used the default ASCII document writer. An independent replay explicitly selects the named transport for both input and output and confirms all60 before/after observations:12 producer positives remain valid,36 malformed relations now reject and12 nonrational weights remain2.5. The positive controls are12 actual ezdxf1.4.4 drawings with48 independently produced spline edges. They cover ordinary and nonuniform nonperiodic knots, rational weights, periodic flags, and the existing2010+ fit/tangent profile. All12 drawings reload through that producer without audit errors or repairs. Source files, generator, module hash and file hashes are pinned under `tests/fixtures/hatch-spline-relations`.

The shared validator now checks positive degree, supplied arrays, finite knot/control/weight values and nondecreasing knots. For nonperiodic splines it also requires at least degree+1 controls and exactly control-count+degree+1 knots. The reader applies this validator to the completed spline packet before accepting the boundary. Export checks every registered block, including model space, paper space, nested definitions and unreferenced definitions, before preprocessing, handle allocation, lazy OBJECTS creation or destination writes. Debug load/save exceptions and Release load-null/save-false conventions remain unchanged.

The writer retains every nondefault stored weight even when73 is zero, while preserving that flag. Default weights remain one where42 is omitted. It does not infer rationality, normalize weights, require positive weights, or change coordinates. Public control arrays remain editable; invalid intermediate states are rejected on save without modifying the document or supplied stream. Explicitly repairing the arrays permits a later save. As before, the file-path Save wrapper itself is not transactional and can truncate a file before stream preflight.

Fit points and optional tangent vectors remain independent stored metadata under the existing2010+ profile. Their order, presence and magnitudes are preserved; no fitting or control regeneration is introduced. Stored periodic packets keep their arrays and flag. The correction does not impose periodic count or closure rules, evaluate periodic shapes, repair geometry, or extend affine-transform support.

The [Autodesk DXF boundary schema](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-DXF/files/GUID-DC5215D6-E73F-4DFF-8BE9-01CA9610FAEE.htm) defines the spline packet fields and optional weight default. The [AcGeNurbCurve2d constructor](https://help.autodesk.com/cloudhelp/2018/ENU/OARX-RefGuide/files/OREF-AcGeNurbCurve2d__AcGeNurbCurve2d_int_AcGeKnotVector__AcGePoint2dArray__AcGeDoubleArray__Adesk__Boolean.html) establishes the nonperiodic count relation. [AcGeKnotVector](https://help.autodesk.com/cloudhelp/2018/ENU/OARX-RefGuide/files/OREF-AcGeKnotVector.html) defines knots as nondecreasing. The constructor describes compact periodic API representations whose counts differ from the independently produced DXF packets; those API rules are not imposed on the wire format without suitable evidence.

A raw inventory at source1a8f9e3 inspected257 tracked DXF/gzip files and67 pinned LibreDWG files, finding56 HATCH records and no spline-edge packet. The R1.4 file starting with EXTENTS remained unparsed. This corpus therefore supplies no positive native spline-edge qualification. The twelve new producer drawings are independent library evidence, not licensed native CAD acceptance.

The independent gate reads indexed optional weights directly from raw packets, checks all stored spline values and flags against the pinned producer source or explicit weight edits, and audits complete outputs separately. The current gate requires 36 outputs containing 144 spline packets and rejects degree, count, descending-knot, weight-loss and rational-flag corruption controls. The initial isolated Debug and Release qualification each passed 1,278 tests: 192 relation/weight cases plus 1,086 existing fit/API/dispatch/scalar cases. Its original 24-output gate passed with zero audit errors or fixes. Raw input serialization already follows `DxfRawDocument.IsBinary`; explicit overload selection and byte-signature assertions make the transport proof visible.

Recovery qualification adds twelve sparse rational-weight cases across all six versions and both transports. Each case explicitly edits a pinned producer packet to omit the first and third control weights, stores -2.5 and negative zero for the second and fourth controls, and retains the rational flag. Three mixed-transport save/reload cycles preserve all stored spline fields, indexed default weights and following geometry. These edited packets qualify storage fidelity; they do not qualify evaluation of curves with zero or negative weights or native CAD acceptance. Every intermediate output now asserts its actual transport signature.

Fresh Debug and Release runs each passed 1,290 tests: 204 relation/weight cases plus the 1,086 adjacent cases. Each independent gate inspected all 36 outputs and 144 spline packets with zero audit errors or fixes. Additional checks against actual output bytes confirmed that the gate fails when a mandatory rational-weight file is missing, a negative weight is lost, or the rational flag changes. Both builds completed with zero errors and 561 existing documentation warnings. Exact source, build, result, verifier and receipt hashes are recorded under `recovery_extension_2026_09_15` in `hatch-spline-qualification.json`; the earlier evidence remains recorded separately.
