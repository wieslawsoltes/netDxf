# Composite Bézier spline knot parameterization

## Correction

A chain of N independent degree-p Bézier spans contains N(p+1) control points and (N+1)(p+1) knots. The repeated boundary knot groups must lie at 0, 1/N, ..., 1. The old constructor divided by the number of boundary groups N+1, not spans N. Its last interval was therefore twice as wide as the others when N > 1. The geometry of each individual span was unchanged, but normalized parameter evaluation reached the wrong location and derivatives with respect to that parameter had inconsistent scaling.

The correction changes the denominator to the number of spans. Both quadratic and cubic constructors benefit, as does the cubic-chain constructor used by fit-point authoring. Null collections, null curve elements and empty chains now reject contextually instead of constructing invalid empty splines or throwing accidental null-reference exceptions. Existing supplied-control/supplied-knot constructors and imported DXF knots are untouched; no existing drawing is automatically reparameterized.

This is a deliberate behavior correction for newly authored composite curves, not bit-identical reproduction of the old constructor's unequal spans. Nonuniform desired parameterization remains possible through explicit knots. Closed/periodic/creation-method serialization flags are a separately identified writer defect and are not claimed corrected here.

## Version/operation contract

All six admitted typed DXF families (AC1015, AC1018, AC1021, AC1024, AC1027, AC1032) retain the corrected authored knot vector through text/binary output, readback and deep clones. The raw API and historical typed admission are unchanged. No curve controls, weights or endpoints are regenerated by this fix.

## Executed evidence

Baseline: merged PR63, `d2c153ff2f33827d33fd9c1897c70c858c25c44c`, tree `5532be0efaba6effef8856e1676f45a5b6aae16d`.

102 new registered cases exercise degree 2/3 chains of 1/2/3/5 spans in all six versions and both transports, plus null/empty constructor cases. Unchanged production: **14,425 pass / 78 fail** in both Debug and Release. Corrected full signed-library suites: **14,503 pass / zero fail**, both configurations. The single-span control cases remain unchanged.

`verify_bezier_knots.py` independently evaluates 48 exported splines in 24 files with ezdxf 1.4.4. It checks all three span midpoints against direct Bernstein-polynomial evaluation, plus endpoints, and requires zero audit errors and repairs. The verifier passes the imported knots directly to ezdxf.math.BSpline because its entity construction_tool rounds them to the stored knot tolerance. The initial construction_tool comparison differed by about 2.5e-7 from exact Bernstein evaluation; the exact-knot evaluator corrects that oracle mismatch without widening its tolerance. This test found the defect while evaluating newly authored HELIX geometry; it does not depend on netDxf's own spline evaluator. Native AutoCAD and rendering have not been executed.

```sh
dotnet run --project tests/netDxf.Conformance -c Debug
dotnet run --project tests/netDxf.Conformance -c Release
python tools/verify_bezier_knots.py artifacts/conformance
```

The span normalization above follows the mathematical construction, not a claim that DXF requires all imported spline knots to be uniform.
