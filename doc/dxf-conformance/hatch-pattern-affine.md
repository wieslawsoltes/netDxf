# Affine HATCH explicit pattern families

`Hatch.TransformBy` maps stored line families of predefined and custom pattern fills through the same affine plane map as their geometric boundaries. Nonuniform scale, shear, reflection and a rank-two world matrix are supported when the HATCH plane and each resulting packet remain representable. Boundaries retain the line/spline and conic behavior qualified by the preceding modules. No rasterization, tessellation, pattern regeneration or third-party implementation is used.

The [Autodesk pattern-data schema](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-DXF/files/GUID-7C05C0EC-B0FB-4A86-A164-B9E5C6C03990.htm) specifies line angle 53, base point 43/44, offset 45/46, dash count 79 and signed dash lengths 49. The [HATCH schema](https://help.autodesk.com/cloudhelp/2023/ENU/AutoCAD-DXF/files/GUID-C6C71CED-CE0F-4184-82A5-07AD6241F15B.htm) separately specifies pattern angle 52, scale/spacing 41, double flag 77 and line count 78. These schema facts are distinct from the managed representation's conversion rules and the actual producer packets pinned by this module.

The twelve fixtures in `tests/fixtures/hatch-pattern-affine` were written through ezdxf 1.4.4 public APIs, reloaded and audited. Six DXF versions use both ASCII and binary transports. Each drawing contains an ANSI33 predefined pattern and a custom pattern with four explicit families, including continuous lines, positive dashes, negative gaps, both signs of zero dots, longitudinal phase offsets and a purely longitudinal offset. The manifest captures actual emitted tags and hashes, rather than assuming the public producer's decimal rounding reproduces the original PAT inputs exactly. Its public API documentation describes the [pattern definitions and signed dash convention](https://ezdxf.readthedocs.io/en/stable/dxfentities/hatch.html).

For netDxf's managed pattern, let global angle/scale be `alpha,s`, local line angle be `beta`, local base be `o`, local offset be `d`, and local dash be `q`. Its existing writer emits `theta=alpha+beta`, `base=s R(alpha)o`, `offset=s R(theta)d`, and `dash=s q`. The offset's local X component carries displacement along a family line; its Y component carries spacing across lines. The separate `Pattern.Origin` is not added to the emitted base. The reader applies the inverse conversion after collecting the global fields.

For the affine map `T(p)=B p+t` between original and transformed HATCH planes, the new wire base is `T(base)` and the new offset is `B offset`. Set `u=(cos(theta),sin(theta))`. The new direction is `B u / |B u|`, and each signed dash is multiplied by the positive factor `|B u|`. This preserves ordered dash/gap intervals and phase under reflections without reversing the sequence or its signs. The implementation retains a compatible global angle/scale based on the transformed original global X direction, then converts every resulting wire field back to local managed values. A save applies the existing writer conversion exactly once.

The prospective packet is reconstructed before commit. Its base, offset and unit direction must match their transformed values within per-coordinate tolerance `1e-10 * max(1, abs(expected.x), abs(expected.y))`; signed dash re-encoding has the equivalent scalar tolerance. All intermediate/output values must be finite. Counts must fit the format's signed-short packet fields. A nonzero dash cannot underflow into a zero dot, and a nonzero local spacing cannot collapse to zero. Exact zero dashes preserve their sign bits through transformation, ASCII/binary writing and reload. These numerical checks describe the supported floating-point mapping; they do not claim exact real arithmetic for arbitrary conditioning.

The separate Origin datum has its own representability contract. Autodesk's [managed Hatch.Origin reference](https://help.autodesk.com/cloudhelp/2024/ENU/OARX-ManagedRefGuide/files/OARX-ManagedRefGuide-Autodesk_AutoCAD_DatabaseServices_Hatch_Origin.html) calls it a WCS `Point2d`, as do the native [originPoint](https://help.autodesk.com/cloudhelp/2018/ENU/OARX-RefGuide/files/OREF-AcDbHatch__originPoint.html) and [setOriginPoint](https://help.autodesk.com/cloudhelp/2018/ENU/OARX-RefGuide/files/OREF-AcDbHatch__setOriginPoint_AcGePoint2d_.html) APIs. This API embeds that stored `(x,y)` datum as WCS `(x,y,0)`, applies the full world transformation and translation, and stores the resulting XY only when its Z is representable as zero. It is never reinterpreted as an OCS base point. The allowed Z roundoff is `8 * 2^-52 * (abs(A31*x) + abs(A32*y) + abs(translation.z))`, evaluated termwise to avoid a sum overflow. There is no absolute floor: a pure tiny nonzero Z translation rejects. A world matrix may move most XY-plane points out of that plane yet remain supported when the actual Origin maps to Z=0. All these checks precede mutation.

The existing netDxf field storage maps the first unbraced ACAD XData 1010 point to this two-coordinate property and writes its Z as zero, preserving later points and unrelated records. The producer fixtures pin that packet behavior separately from the WCS API contract. Autodesk's [native XData example](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-AutoLISP/files/GUID-1A2A0518-E9DB-462E-925E-32181D96CE4D.htm) provides an ACAD 1010 example; it does not establish a complete ACAD application-data schema or native behavior for every arbitrary-plane transform. Actual-output checks compare both changed and unchanged Origin packets and all unrelated ACAD content. No native AutoCAD execution is claimed.

Explicit nonuniform support is limited to predefined/custom fills with at least one stored line family and `IsDouble=false`. [Autodesk's pattern-type reference](https://help.autodesk.com/cloudhelp/2019/ENU/OARX-RefGuide/files/OREF-AcDbHatch__HatchPatternType.html) gives user-defined patterns implicit linetype/spacing/angle semantics and a possible perpendicular second family. This module conservatively rejects non-similar maps when group 77 is true even for predefined/custom fills; it does not assume explicit lines exhaust that flag's meaning. User-defined and gradient non-similar transforms remain separate unsupported cases. Similarities retain their preceding behavior. Unknown pattern subclasses reject nonidentity transforms because their additional storage has no explicit transformation contract.

Validation constructs a standard `HatchPattern` snapshot and copies each line and dash without invoking virtual `Clone`. All boundary, plane, seed, origin and pattern checks finish before associative source unlinking, path callbacks or any replacement. On success the transformed HATCH owns its new snapshot; another HATCH sharing the old pattern keeps the original object and every line/dash unchanged. On rejection all original pattern/path identities, source occurrences/reactors, handles and document membership survive. Exact identity with zero translation preserves original stored objects. Application event-handler exceptions during a successful mutation remain outside the prevalidation guarantee.

Qualification includes sampled world family/phase/dash points from actual output, independent OCS reconstruction, source/output wire comparisons, unchanged unrelated ACAD payload, mixed stored spline controls/fits/tangents/weights, shared pattern ownership, repeated transformations and atomic refusals for invalid or unrepresentable packets. Complete final counts, DLL/source identities and before/after results are recorded in [qualification.json](receipts/hatch-pattern-affine/qualification.json). This does not claim native CAD rendering, pattern regeneration or gradient support.
