# Affine HATCH conic boundaries

`Hatch.TransformBy` transforms circular arcs, elliptic arcs and active polyline bulges directly in the HATCH plane. A nonuniform scale or shear can turn a circular arc into an ellipse edge. Existing ellipse edges remain ellipses with orthogonal major/minor axes; spline packets in the same HATCH continue through the storage-preserving affine route, retaining their knots, flags, weights and optional fit metadata. No tessellation, curve fitting or third-party implementation is used.

For an input conic, write its point as `center + u cos(t) + v sin(t)`. Transform the center as a position and the two axes as vectors using the affine plane map. A scaled two-dimensional symmetric eigensystem supplies the orthogonal major direction and largest singular value. The smaller singular value is `abs(det[u v]) / largest`, which avoids subtracting nearly equal eigenvalues. The output ratio is positive and at most one. Endpoint angles are reconstructed in those axes, and the direction flag follows the orientation of the transformed axis pair. This accommodates axis swaps, shear, reflections, tilted original planes and matrices that retain a two-dimensional image plane.

The [Autodesk HATCH boundary-path schema](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-DXF/files/GUID-DC5215D6-E73F-4DFF-8BE9-01CA9610FAEE.htm) identifies ellipse center/major-axis/ratio fields, start/end angle fields 50/51 and counterclockwise flag 73. The schema alone does not resolve every angular convention. This module separately pins actual ezdxf 1.4.4 producer packets in `tests/fixtures/hatch-conic-affine`: the generator calls the public producer API, captures raw writer tags, writes ASCII and binary drawings, and reloads/audits the drawings. The manifest records API angles, raw tags and every file hash. The verifier checks raw parsed packets against those captures before interpreting output geometry.

For these producer packets and netDxf's stored boundary representation, ellipse angles are polar angles relative to the major-axis direction. They differ from the eccentric parameter `t`: `tan(t) = tan(polarAngle) / ratio`, with the quadrant retained. Clockwise packets store the negatives of physical endpoint angles while keeping the actual start/end order. For example, producer API angles 30/150 with `ccw=False` emit raw angles 210/330; the physical start is at 150 degrees and the physical end is at 30 degrees. ezdxf's normalized in-memory objects reorder endpoints, so their parameter properties alone are not the evidence for this wire convention. See the public [HATCH boundary API documentation](https://ezdxf.readthedocs.io/en/stable/dxfentities/hatch.html).

An exact raw start/end equality denotes a zero interval. An exact absolute raw difference of 360 denotes one full turn. A nonzero shorter difference denotes the directed interval between the physical endpoints. More than one stored turn rejects. A transformed full turn uses a common floating-point grid for both endpoints so their stored difference remains exactly 360 across later transforms. Near-full intervals remain distinct from full turns. Exact identity plus zero translation preserves the original edge objects and their original angle spelling.

The [Autodesk bulge definition](https://help.autodesk.com/cloudhelp/2018/ENU/OARX-RefGuide/files/OREF-AcDb2dVertex__bulge.html) gives `bulge = tan(includedAngle / 4)`, negative for clockwise segments. A bulge is considered straight only when its stored value is exactly zero. A similarity retains the polyline representation, vertex count, closure and dormant terminal bulge; reflections reverse active bulges. A non-similarity expands curved segments to ellipses and straight segments to lines, preserving segment order and all path classification bits except the polyline representation bit. Open polylines acquire no closing segment. If an open polyline must change representation and its unused terminal bulge is nonzero, the operation rejects rather than discarding that stored value.

Very small nonzero bulges produce very large circle centers and radii. Even finite ellipse fields can then lose the original endpoints through cancellation or angular precision. Before committing, the implementation reconstructs both endpoints from the prospective stored conic packet and requires each coordinate to differ from its independently transformed input endpoint by no more than `1e-10 * max(1, abs(start.x), abs(start.y), abs(end.x), abs(end.y))` in the new HATCH plane. For a bulge segment, those expected endpoints come from its original vertices; its large derived center/radius cannot enlarge the tolerance. Unrepresentable conics reject atomically. Tiny nonzero bulges are never silently flattened. An exact rational-quadratic fallback for rejected bulges is separate work.

All original inputs, temporary output paths, plane coordinates, seeds and pattern state are validated before source unlinking or path callbacks. Invalid radii/axes/ratios, collapsed or unrepresentable results, unsupported intervals and terminal-bulge loss preserve path identities, association references/reactors, registered membership, handles and pattern state. Successful transforms keep the existing explicit unlink behavior; former source entities retain their identities and geometry. Exceptions thrown by application event handlers during a successful mutation remain outside the prevalidation guarantee.

The geometric boundary support applies to solid fills. General affine pattern/gradient rendering still cannot be represented by the existing scalar angle/scale controls and remains explicitly rejected. Similarities retain the existing pattern behavior. This work does not claim native AutoCAD open/AUDIT/save/reopen, rendering parity, spline evaluation or general associative regeneration.

Qualification and exact source/output hashes are recorded in [qualification.json](receipts/hatch-conic/qualification.json). The positive corpus covers six DXF versions, both transports, seven transforms and two original planes, including 1,000:1 anisotropy. Independent verification parses actual output packets, reconstructs the OCS basis separately, probes world-coordinate curves, checks zero/full intervals and audits complete drawings without repairs. Additional tests cover repeated transforms, tiny-bulge conditioning, associated rejection and mixed stored splines.

Final owner qualification passed **9,040 unique HATCH cases in each of Debug and Release**, with identical result hashes. The 205 new cases passed 16/205 against the frozen preceding affine module and 205/205 against the final source using the same test binary. Each final configuration passed all **22 independent HATCH gates**. The conic gate checks 168 main drawings containing 6,216 segments with 404,040 world-coordinate probes, plus 14 accepted tiny-bulge drawings and two mixed-conic/spline drawings containing eight preserved spline packets. All 184 drawings audit without errors or repairs, and seven corruptions of actual output are rejected, including a direction-bit change on a zero-length interval. The 56-input conditioning probe accepts 14 conic representations and atomically rejects 42; accepted magnitudes reach 1e-6 for the tested shear and 1e-5 for the tested nonuniform scale.

All five Release library targets (netstandard2.0, net471, net48, net6.0 and net8.0), plus Debug netstandard2.0, compile with zero errors and exactly 561 existing CS1591 warnings per target. Debug net8 has the same warning inventory; the Release test build reuses its already-qualified library. No warnings are suppressed. The conic implementation removes the obsolete legacy transform method and its incomplete XML parameter documentation.

A separate frozen reviewer harness also passes on the same 168 final main drawings. It uses ezdxf construction primitives and OCS with independently composed transformations, checking 6,216 segments and 254,856 ordered world-coordinate samples. Its maximum absolute error is 1.32e-9 on the large anisotropic coordinates, with zero audit errors or repairs. The exact harness, final per-file results, DLL identity and source revision are preserved beside the qualification receipt. These are additional checks of the same drawing corpus, not additional output cases.
